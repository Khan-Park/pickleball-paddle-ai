# T-032 실시간 최저가 조사 (조사만)

## 목표
앱 안에서 제품별 "지금 최저가"를 보여 주는 방안(쇼핑 검색 API)이 **우리 조건에서 가능한지** 사실을 모으고, 구현할지 사용자가 정할 수 있게 선택지를 정리한다. 이 카드에서는 코드를 바꾸지 않는다(D5: M2에서는 조사만). 기획: docs/plan/m2.md 3장 D·9장 D5, phase2 4장 M2·8.1.

## 우리 조건 (조사할 때 기준)
- 사이트는 Cloudflare Workers의 정적 파일(무료)이고 서버 코드가 없다(D-027). 주소는 workers.dev 하위 도메인
- 비밀값은 `.env.local`에만, 서버 코드에서만 쓴다(CLAUDE.md 규칙 6). 브라우저에 API 키를 넣을 수 없다
- 추천 엔진은 구매·가격 비교 정보를 읽지 않는다(규칙 1). 최저가는 화면 표시용이다
- 가격은 사람이 확인한 판매처 가격을 보여 주고 있고(30일 재확인), 자동 수집은 하지 않기로 했다(판매처 약관 문제, phase2 4장)
- 수익(쿠팡 파트너스)은 M3. 지금은 비상업에 가깝지만 곧 제휴 링크가 들어간다

## 조사 질문
1. **네이버 쇼핑 검색 API**(네이버 개발자센터 검색 API의 쇼핑)
   - 이용 약관: 상업 이용(제휴 수수료를 받는 사이트) 허용 여부, 결과 표시 의무(출처·로고·링크), 결과를 저장·가공·재배열해도 되는지, 캐시 허용 기간
   - 무료 한도(일 호출 수), 초과 시 동작, 키 발급 조건(사업자 필요 여부)
   - 응답 항목: 상품명·최저가·판매처·링크·이미지. 같은 모델만 고를 수 있는지(카테고리·브랜드·제품 번호 필드)
2. **다른 선택지**: 다나와·쿠팡(파트너스 API)·기타 가격 비교 API의 공개 여부와 조건(간단히)
3. **서버 기능**: API 키를 숨기려면 Cloudflare Worker 코드(정적 파일 + Worker 스크립트)가 필요하다
   - Workers 무료 요금의 요청 한도·CPU 한도, 정적 파일과 Worker를 한 프로젝트에 같이 두는 방법(공식 문서)
   - 대안: 빌드할 때 API를 불러 가격을 파일로 굳히는 방식(배포 시점 가격). 약관상 저장·재표시가 허용되는지가 관건
4. **정확성 위험**: 검색 결과에 다른 모델·중고·부품이 섞이는 정도. 우리 제품 2~3개로 실제 검색어(`compare_query`)를 넣었을 때의 결과 예시(가능하면)

## 진행
1. **fury(외부 조사)**: 위 질문의 사실을 공식 문서·약관 원문에서 모은다. 원문 인용(짧게)·주소·확인일, 확인 못 한 것은 "미확인". 결과물: `docs/plan/t-032-research.md`
2. **메인 세션**: 조사 결과를 읽고 선택지 표(하지 않음 / 빌드 때 굳히기 / Worker로 실시간 / M3 이후)를 만든다. 선택지가 갈리고 약관 해석이 걸리면 strange(권고안)를 부를지 그때 판단한다
3. **hawkeye(독립 검토)**: 약관·한도 같은 "틀리면 비용이 큰 사실"의 출처와 인용이 원문과 맞는지 검증한다(조사 결과가 구현 결정의 근거가 되므로)
4. 사용자가 구현 여부를 정한다. 구현하면 별도 카드
